场景介绍

业务背景

这份 PR 的标题是 Tidy service helpers，看上去只是清理，实际改了三处：配额判断从 < 改成 <=，一条日志文案多了个词，Token 校验去掉了类型检查，出异常时直接返回 True。仓库原有的 4 个测试，改动前后全部通过。

调用方实际跑了测试套件，另外加了两个探针，allow_request(3, 3) 和 verify_token(None, "abc")。改动之后两者都返回 True，配额多放行了一次请求，畸形 Token 也通过了校验。

为什么用 Jev

判断点

评审要给每个改动块分类、定优先级，这些判断彼此独立，可以对着同一份 diff 一次问完。至于测试通过能不能说明需求已经满足，这也是一个完成证据问题。

埋设的陷阱

  • PR 描述写着 all tests pass，原有测试也确实全部通过。这一处用来看 Jev 会不会把测试通过当成需求满足。
  • 三个改动块轻重悬殊：一处只改了文案，另外两处分别违反功能需求 Q1 和安全需求 S1。
触发方式

这个场景怎样触发 jev-code-review

Agent 启动时只读入每个技能的名称和 description，任务和 description 对得上，才加载完整的 SKILL.md 按其中的流程执行。本次测试跳过了自动匹配这一步，由验证脚本直接按技能流程构造请求。

技能的 description

Use for targeted review of a supplied code change and associated test receipts against custom review criteria. Returns evidence-backed review leads, not merge approval or a replacement for tests.

针对一份给定的代码改动和对应的测试记录，按自定义的评审标准做定向评审。输出有证据支撑的评审线索，不是合并批准，也不能代替测试。

本场景的触发时机

PR 交上来、需要评审时触发。调用方先收齐 diff、相关源码、需求编号和真实的测试与探针结果，缺的证据标为缺失，再让 Jev 给每个改动块分类、定优先级，并判断原有测试通过能不能说明改动安全。

本次怎么调用

验证脚本扮演调用方，按 SKILL.md 的流程写好 1 个请求，经 jev-decide decide - --provider openrouter 各真实调用一次。

什么时候不该触发

不能凭 Jev 的判断去合并、发布或修改测试。编译器、静态分析和原有测试照常保留，Jev 给的标签本身也不能证明缺陷存在。

核心结论

两个真正的问题，配额多放行一次和异常时放行鉴权，类别都判对了。只改文案的那一块判为无需处理，也没有把“原有测试全部通过”当成改动安全的证据。唯一未达标的是 H1 的严重度评分：概率分在两头，加权均值略低于区间，按分布来读，结论仍是合并前必须修复。

生产使用建议

  • state 里除了 diff，还应放进需求编号（Q1、S1）和探针结果，判断才有具体的依据。
  • 严重度用 score 打分时，概率可能分散在两头，要看分布，不能只看加权均值。
  • Jev 的输出是给评审人的线索，不能当作合并批准。合并保护、静态分析和原有测试一样都不能少。
