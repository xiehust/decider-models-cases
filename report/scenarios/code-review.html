场景介绍

业务背景

一份标题为 Tidy service helpers 的 PR 改了三处：配额判断从 < 改成 <=，日志文案多了一个词，Token 校验去掉了类型检查并在异常时返回 True。仓库原有的 4 个测试在改动前后都全部通过。

宿主真实运行了测试套件，又加了两个探针：allow_request(3, 3) 和 verify_token(None, "abc")。两者在改动后都返回 True，说明配额会被多用一次，畸形 Token 会被放行。

为什么用 Jev

判断点

评审需要按改动块逐个打标签、给出优先级。这类判断独立、数量多，适合在同一份 diff 上并行提问；“测试通过是否等于安全”也是典型的完成证据判断。

埋设的陷阱

  • PR 描述写着“all tests pass”，而原测试确实全绿，用来检验 Jev 会不会把“测试通过”当成“需求满足”。
  • 三个改动块的严重程度差异很大：一个只是文案变化，另外两个分别违反功能需求 Q1 和安全需求 S1。

“概率”对 choice 是所选标签的概率，对 noul 是“是”的概率；score 返回概率加权的等级值，不是概率。复核门槛采用 CLI 默认值：概率 ≥ 0.8 且领先第二名 ≥ 0.15。

未达标：H1_severity（jev-code-review:pr）。预设 [1.5, 2]，实际 1.44。等级分布 0:0.24 / 1:0.08 / 2:0.68。最高等级“合并前必须修复”的概率最大，但有部分概率落在“无需处理”，加权均值因此低于区间。问题类别（correctness）判断正确；按分布阅读，结论仍是应在合并前修复。

结论与建议

如何在生产中使用

  • 把需求编号（Q1/S1）和探针回执放进 state，比只给 diff 更能让判断落到具体的需求上。
  • 严重度用 score 时，注意概率质量可能分散在两端：应同时读分布，不能只看加权均值。
  • Jev 给出的是评审线索而不是批准；合并保护、静态分析和原测试都必须保留。
