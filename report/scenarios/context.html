🗂️ 长会话上下文压缩

压缩会话前，先判断 8 个上下文块哪些能删。既要分清真重复和近似重复，又要留住阶段已经结束、内容仍然有用的记录。

场景介绍

业务背景

一次数据迁移排障下来，会话里堆了大量工具输出。压缩上下文时，删掉无关日志风险不大，麻烦在于把看起来相同的报错当成重复删掉，或者丢掉一个阶段早已完成、回滚时却还要用的快照 ID。

本场景只给出保留或丢弃的建议，会话记录一律不动。

决策模型的用途

判断点

每个块单独问一个问题，全部块可以在一次请求里判断完。主模型不必为了压缩再把整段历史读一遍。

埋设的陷阱

  • B2 与 B3 一字不差，是真重复。B4 和它们只差一个 refund_id（F-1180 对 F-1193），属于近似重复。
  • B5 记录阶段 1 已经完成，可其中的快照 ID 回滚时必须用到。
  • B6、B7 是和目标无关的成功日志。

Skill 触发方式

这个场景怎样触发 jev-context

这里保留本场景对应的 Jev Skill 定义与原始调用方式，说明用例来源和接入方法。其他参评模型使用相同的 state / questions 进行判断对比。

Agent 启动时只读入每个技能的名称和 description，任务和 description 对得上，才加载完整的 SKILL.md 按其中的流程执行。本次测试跳过了自动匹配这一步，由验证脚本直接按技能流程构造请求。

技能的 description

Use when large tool results need relevance review or a user wants advice about a compaction checkpoint. Starts with a keep/drop proposal; does not install hooks or automatically rewrite agent memory.

工具输出太多、需要判断哪些还相关，或者用户想在压缩上下文之前听听建议时使用。先给出保留或丢弃的建议，不安装钩子，也不自动改写 Agent 的记忆。

本场景的触发时机

长会话快到上下文上限、准备压缩时触发。调用方先把原文存好、随时可以召回，再把会话切成带 ID 的块，每块问一次保留还是丢弃。看起来重复的块，另用一个是非题核对是不是同一条记录。

本次怎么调用

验证脚本扮演调用方，按 SKILL.md 的流程写好 1 个请求，经 jev-decide decide - --provider openrouter 各真实调用一次。

什么时候不该触发

真正的压缩只能由调用方原生支持的操作完成，而且要经过授权。什么时候压缩是另一个问题，不靠这个技能判断。

原始 Jev 实验与调用方核验 · 补充证据

以下记录最初的 Jev 实验、概率分布和宿主执行结果。它们解释测试集如何产生，不作为其他模型已经完成闭环的证明。三种决策模型的横向结论以上方同题评测为准。

Jev 原场景验证

Jev 严格验收、结论与建议

测试结果

  • 9/9 个判断符合标准答案，0 个进入 needs_review。
  • 没有未达标的判断。

核心结论

真重复和近似重复分得清：只建议丢掉一字不差的重复块和无关日志，保留了只差一个 refund_id 的近似块，以及回滚时要用的快照记录。整个过程在影子模式下运行，会话记录没有被改动。

生产使用建议

  • 保留策略里要写明，只有完全相同的块才算重复。近似块是否指同一条记录，另用一个 noul 问题核对。
  • 先在影子模式下跑，把会被隐藏的块列给用户确认，再接入真正的压缩操作。
