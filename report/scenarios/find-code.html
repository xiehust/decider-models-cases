场景介绍

业务背景

新成员常问支付回调的签名在哪里校验、重试间隔在哪里计算。关键字搜索容易被同名符号带偏：这个仓库里，hmac 同时出现在支付回调和密码重置两个文件中，RETRY_MAX 常量写在 config.py，退避时间却在 retry.py 里算。

仓库里也没有密码重置邮件的正文，templates.py 只定义了发货和收款两个模板。

为什么用 Jev

判断点

候选都是调用方实际读过的文件和源码，Jev 只在其中挑选。调用方随后打开文件核对符号，选错了可以退回，路径不会凭空编出来。

埋设的陷阱

  • hmac.compare_digest 在 passwords.py 和 webhooks.py 里都有。
  • 和重试有关的代码分在两处，次数在 config.py，退避计算在 retry.py。
  • templates.py 从名字看像是放邮件模板的地方，里面却没有密码重置模板。
触发方式

这个场景怎样触发 jev-find-code

Agent 启动时只读入每个技能的名称和 description，任务和 description 对得上，才加载完整的 SKILL.md 按其中的流程执行。本次测试跳过了自动匹配这一步，由验证脚本直接按技能流程构造请求。

技能的 description

Use for natural-language repository navigation or choosing which observed files to inspect next. Works with supplied paths and summaries; not a replacement for required graph search or exact symbol lookup.

用自然语言在仓库里找代码，或者在已经看到的文件里挑下一个要看的。只在给定的路径和摘要中选择，不能代替项目要求的代码图谱搜索或精确的符号查找。

本场景的触发时机

有人用一句话问某个功能在哪里实现，关键字搜索又给出好几个候选时触发。调用方把真实路径和读到的文件摘要整理成候选交给 Jev，候选里留一个 none。

本次怎么调用

验证脚本扮演调用方，按 SKILL.md 的流程写好 1 个请求，经 jev-decide decide - --provider openrouter 各真实调用一次。

什么时候不该触发

已知符号名时直接精确查找，项目要求先用代码图谱或索引的，先用它们。Jev 选出文件后，还要打开文件核对。

测试结果

  • 4/4 个判断符合标准答案，1 个进入 needs_review。
  • 没有未达标的判断。

核心结论

三个功能都定位到了正确的文件，调用方打开文件后确认了对应的符号。仓库里并不存在的密码重置邮件模板，它返回 none 并进入复核，没有挑一个看上去相近的文件来充数。

生产使用建议

  • 仓库大的时候，先用代码图谱或索引缩小范围，再让 Jev 在读过的候选里按语义挑选。
  • 选出文件之后，还要用确定性工具确认符号确实存在。
