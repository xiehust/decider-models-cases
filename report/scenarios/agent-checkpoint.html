🧭 Agent 执行检查点

重复失败时换路、计划偏航时拉回、把“排队中”误报为“已完成”时拦截。

9/9 通过 · 复核 0判断数 9 模型 typesafe/jev-1.13-20260917运行日期 2026-10-12
场景介绍

业务背景

长任务中的编码 Agent 最常见的三种失误是：同一条失败命令反复重试；做着做着偏离用户真正的需求；把“已触发”“排队中”当成“已完成”向用户汇报。这些都不是缺少知识，而是在关键节点缺少一次冷静的判断。

本场景在三个检查点各给 Jev 一份完整状态：目标、用户规则、命令回执和候选动作。只让它回答“下一步选哪个”“这个说法是否成立”“完成证据有多强”。真正执行仍由宿主负责。

为什么用 Jev

判断点

检查点判断频繁、答案空间很小、需要的是证据对照而不是长篇推理。这正是类型化判断的长项，比让主模型再想一遍便宜得多。

埋设的陷阱

  • 恢复场景：三次相同的 ModuleNotFoundError；候选里混入了“装进系统 Python”这一违反用户规则的捷径。
  • 偏航场景：计划中途开始重写日志框架、升级 pandas，而用户要求“改动尽量小”。
  • 完成场景：流水线处于 running，健康检查仍返回旧版本 2.3.0，但 Agent 已声称“部署成功”。

结论与建议

如何在生产中使用

  • 在“重复失败 ≥2 次”“即将向用户报告完成”“计划步骤数超出预期”时插入检查点，而不是每一步都问。
  • 完成判断要同时问 noul（主张是否成立）和 score（证据强度），两者互为校验。
  • 把用户规则逐条写进 state；Jev 能识别违规候选，但拦截动作仍应由宿主的权限系统执行。
