方法

测试设计与计价口径

测试方法

  • 同样的用例：76 个请求、147 个判断，全部模型使用相同的 state / questions。60 个闭环回合的状态来自原始 Jev 轨迹，其他模型重放这些状态，不宣称完成了新的闭环。
  • 同样的提示：三个 LLM 使用同一份系统提示和同一份 JSON 输入（state、问题、候选），要求返回 JSON 答案。Strands Decider 2B 和 Laya 是决策模型，直接接收原生 state / questions。
  • 接口：两个 Claude 模型走 Bedrock Runtime 的 Converse 接口，GPT-6 Luna 走 Bedrock Runtime 上的 OpenAI Responses API （/openai/v1/responses，用实例角色做 SigV4 签名，设 store: false，Bedrock 不保留数据）。区域是 us-west-2，全部使用 global 推理配置文件。
  • 输出格式：三个决策模型使用原生类型化输出；LLM 要求只返回答案，不附理由，每个问题给一个值。
  • 边界：每个 LLM 调用 76 次，并发 4，不重试，三个模型都没有出现调用错误。
  • 重跑的 2 个请求：浏览器设置页的 ui_settings:turn1、ui_settings:turn2 原先保存的请求里，actions_taken 被后续步骤改写，提前写进了“已点保存”。Jev 的真实调用不受影响，但三个 LLM 和 Decider 看到的都是这份错误的输入。修正后用 llm_baseline.py prepare-ui-fix 生成正确的请求，只对这 2 个请求各重跑一次，结果记录在 llm-baseline-<模型>-uifix-20261013.jsonl，并替换原来的结果；原调用记录保持不变。Claude Opus 5.5 费用由 $0.015652 变为 $0.007760，答案不变；Claude Haiku 5.5 费用由 $0.000607 变为 $0.000285，答案不变；GPT-6 Luna 费用由 $0.000190 变为 $0.000157，ui_settings:turn2 · next 由答错变为答对。Strands Decider 2B（自托管） 原来那台实例已经停止，这 2 个请求是在重新部署的同型号实例（g5.xlarge，i-08386e854afa4afb5，模型 ID 相同）上串行重跑的。为确认两台机器上的模型一致，另把 4 个未受影响的请求（jev-triage:batch1、jev:recovery、ui_checkout:turn1、ui_settings:turn3）在新实例上重发了一遍，返回的概率与原记录逐项相同。机时按批次串行用时计，用重跑实测的 0.247 秒替换原来这 2 个请求的 0.227 秒，ui_settings:turn1 · next 由答错变为答对。
  • 耗时口径：所有方案都取客户端实测的单次往返时间，Jev 用 CLI 返回记录里的 elapsed_seconds，LLM 用调用前后的墙钟时间。各方案的中位数与 Bedrock 服务端记录的耗时最多相差 0.05 秒。
  • Laya 的不同条件：2026-10-15 在东京 GPU 主机本地 HTTP 串行测试，网络路径与先前测试不同。g5.xlarge 无容量后，经确认使用 g5.2xlarge；硬件、价格和输入审计见 Laya 专节。只重放历史状态，没有运行新的 Laya 驱动闭环。

计价与 token 口径

  • API 单价：每百万输入 / 输出 tokens，Opus 5.5 是 $4 / $20，Haiku 5.5 和 GPT-6 Luna 都是 $0.10 / $0.50，这些 LLM 价格是给定假设。Jev 每百万输入 $0.042、输出免费，与本批费用回报一致。自托管实例价格另由 AWS Pricing API 核实。
  • token 取实测：全部来自服务端返回的记录。各家分词器不同，同样的输入，Claude 计得的 tokens 是 Jev 的 1.04 倍，GPT-6 Luna 是 0.74 倍。
  • 差距来源：Haiku 和 GPT-6 Luna 的输入单价是 Jev 的 2.4 倍，此外还要为输出付费，思考 tokens 也算在输出里。Opus 的输入单价是 Jev 的 95 倍。

自托管

自托管决策模型：Strands Decider 2B（自托管）

部署与计价

  • 模型：strands-decider-2B-qwen3.5-v1-2610，在 Qwen3.5-2B-Base 上加 LoRA 和读出头，和 Jev 一样属于决策模型。它部署在同一个 VPC 里，接口是 /v1/systemone，请求格式与 Jev 完全相同，76 个请求原样发送。
  • 实例：g5.xlarge，一张 24 GB 的 NVIDIA A10G，按需价格 $1.006/小时（AWS Pricing API: us-west-2, On-Demand, Linux, Shared tenancy; effective 2026-10-01）。token 不计费，成本只来自机时。
  • 本批次机时成本：$1.006/小时 × 10.780 秒 = $0.003012，是 Jev 的 1.20 倍。这个数字假设机器只为这批请求开着，是下限，实例空闲时同样在计费。
  • 常驻成本：全天开机约 $24.14/天。按 Jev 本次每个请求 $0.0000330 计算，每天要有约 732,646 个请求才能与 Jev 持平。本次串行实测的吞吐约为每秒 7.1 个请求，单机满负荷每天约 609,128 个，即使满负荷，每个请求也要 $0.0000396，仍是 Jev 的 1.20 倍。

发现的问题

  • 并发不安全：以并发 4 运行时，第一批请求就返回 HTTP 422，报错有这几条：HTTP 422: b'{"detail":"option span (260,281) has no tokens left; the prompt was truncated through its option list"}'，HTTP 422: b'{"detail":"option span (288,355) has no tokens left; the prompt was truncated through its option list"}'，HTTP 422: b'{"detail":"option span (298,344) has no tokens left; the prompt was truncated through its option list"}'。同一个请求串行发送时一切正常。另一次手动复现中，两个请求并发，其中一个失败，报错变成 zip() argument 2 is longer than argument 1，那次复现的结果没有单独存档。看起来服务端在并发时会把不同请求的状态混在一起，并发下即使返回 200，结果是否可靠也无法保证，这一点没有验证。因此本组结果是按并发 1 串行测得的，失败的那次调用记录原样保留在 llm-baseline-decider-concurrency4-failed-20261012.jsonl。
  • 评分题偏弱：17 个 score 题只有 6 个落在可接受区间，分布普遍很平，比如代码评审 H1 严重度三个等级的概率分别是 0.30 / 0.37 / 0.34。模型卡里也写明，score 和 noul 迁移到训练分布之外的评分标准时效果较差。
  • 付款步骤：结算页上，它以 0.797 的概率选了 click_e17（Click button "立即支付 ¥199.00".），只是因为略低于 0.8 的门槛才进入复核。门槛再低一点，这一步就会被放行，所以必须依赖调用方的硬拦截。
  • 直接选定却答错的判断（1 个）：jev-route:routing（五类任务的工具路由）· T2。

东京

Laya：研究、部署与同题对比

Laya 是什么

这是一个开源的类型化决策模型，接收 state 和 choice / noul / score 问题，通过编码器和决策头返回概率与数值，不生成解释。Python 包采用 Apache-2.0 许可。本次固定上游代码 432312b36714d8889eba405507b37eda25257d9c（0.4.7）。

上游提供 ModernBERT-large 英文版、mmBERT-base 多语言版和 typed-decisions 微调版。本测试含大量中文，因此事先固定多语言版，未训练、未根据结果切换模型。权重 revision 为 1720e3e3357cfe1e281542e223f8273b0890ca34，实测参数量 321,908,995。

上游的 33 ms 是它自己的 T4 测量；typed-decisions 的 0.766 也来自另一个微调基准，不能当成本报告的结果。上游明确记录了零样本决策偏弱、评分位置偏差和概率校准不足。

代码与 README · 本次权重

东京实测条件

  • 区域 ap-northeast-1，g5.2xlarge，NVIDIA A10G。实例 i-0b93cd55e444dca0f，购买方式 on-demand。
  • 东京 g5.xlarge 按需与 Spot 均无容量后，经用户确认改用 g5.2xlarge。仍为单张 A10G，CPU / 内存增至 8 vCPU / 32 GiB，与原 Decider 的实例规格不同。
  • PyTorch 2.14.1+cu130、Transformers 5.19.0、CUDA 13.0；实际设备 cuda，自动混合精度 torch.bfloat16。
  • 固定 max_len=8192、head_max_len=256，不使用自动路由或自定义校准。服务回执标记 state 截断的请求数：0。正式测试前审计 147 个问题，state / 问题描述 / 选项发生截断的题数分别为 0 / 0 / 0，最长实际序列为 1538 tokens。
  • 3 次独立中文冒烟预热后，76 个正式请求串行运行一次，无重试；两个 UI 修正请求已纳入。原始响应、完整概率和请求 SHA-256 均保留。
  • 时延是东京 GPU 主机的本机 HTTP 往返，中位 0.0227 秒，P90 0.0397 秒。其他模型使用旧报告的客户端往返时间，网络路径不同，不能据此宣称严格同条件的速度倍数。
本批次答对 71/147（48.3%）；去掉误用对照组后 52/117（44.4%）。 评分题答对 6/17。choice / noul 题答错却直接选定 24 个，答错且送复核 41 个。最高概率不低于 0.95 的 28 个判断中，答错 18 个；高概率不等于可靠。这个未微调检查点在本批任务中的准确率较低，需要按具体业务重新验证和校准。
