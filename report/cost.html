摘要

结论

最便宜的 LLM 也要花 Jev 的 3.1 倍。GPT-6 Luna $0.0078，Haiku 5.5 $0.0137，Jev 是 $0.0025。两者单价相同，GPT-6 Luna 却比 Haiku 便宜约 43%，因为它计得的输入 tokens 少约 29%，输出也更短。
Haiku 5.5 的准确率最高。答对 146/147，没有请求被过滤，答错的是 jev-triage:batch3（工单分诊批次 3（K09–K12））· K09_urgency。Opus 5.5 能作答的判断全部答对，但有 1 个请求（jev-redteam:R1）被内容过滤。
三个 LLM 里，GPT-6 Luna 最快、最便宜，错得也最多。答对 141/147，答错的判断分布在红队评估 4 个、工单分诊 2 个。
Jev 的错题和 LLM 不在一处。Jev 主要错在网格独自规划（18 个回合），其余 3 个是 jev-code-review:pr（“小清理”PR 中的越界与失败放行）· H1_severity、jev-triage:batch1（工单分诊批次 1（K01–K04））· K01_urgency、jev-triage:batch3（工单分诊批次 3（K09–K12））· K10_urgency，这些题 LLM 基本都答对了。下文的组合方案先交给 Jev、再把需复核的请求转给 Haiku，费用约为纯 Jev 的 3.3 倍。
自托管的 Strands Decider 2B 最快，在这批用例上却明显不准。串行中位 0.11 秒，按 g5.xlarge 机时折算 $0.0030，是 Jev 的 1.2 倍。它答对 98/147，不含网格误用对照组时为 92/117。在有复核状态的 choice / noul 题里，它答错的 38 个中有 37 个已被自己送去复核，直接选定却答错的只有 1 个。另有 11 个评分题超出可接受区间。服务端在并发时不安全，只能串行。
方法

测试设计与计价口径

测试方法

  • 同样的用例：76 个请求、147 个判断，和 Jev 运行时看到的完全一致。60 个闭环回合按 Jev 当时的调用记录回放，在同样的状态下重建请求。
  • 同样的提示：三个 LLM 使用同一份系统提示和同一份 JSON 输入（state、问题、候选），要求返回 JSON 答案。Strands Decider 2B 是决策模型，直接接收与 Jev 相同的原生请求，不用提示。
  • 接口：两个 Claude 模型走 Bedrock Runtime 的 Converse 接口，GPT-6 Luna 走 Bedrock Runtime 上的 OpenAI Responses API （/openai/v1/responses，用实例角色做 SigV4 签名，设 store: false，Bedrock 不保留数据）。区域是 us-west-2，全部使用 global 推理配置文件。
  • 输出格式：要求 LLM 只返回答案，不附理由，和 Jev 一样每个问题给一个值。
  • 边界：每个 LLM 调用 76 次，并发 4，不重试，三个模型都没有出现调用错误。
  • 重跑的 2 个请求：浏览器设置页的 ui_settings:turn1、ui_settings:turn2 原先保存的请求里，actions_taken 被后续步骤改写，提前写进了“已点保存”。Jev 的真实调用不受影响，但三个 LLM 和 Decider 看到的都是这份错误的输入。修正后用 llm_baseline.py prepare-ui-fix 生成正确的请求，只对这 2 个请求各重跑一次，结果记录在 llm-baseline-<模型>-uifix-20261013.jsonl，并替换原来的结果；原调用记录保持不变。Claude Opus 5.5 费用由 $0.015652 变为 $0.007760，答案不变；Claude Haiku 5.5 费用由 $0.000607 变为 $0.000285，答案不变；GPT-6 Luna 费用由 $0.000190 变为 $0.000157，ui_settings:turn2 · next 由答错变为答对。Strands Decider 2B（自托管） 的这 2 个请求还没有重跑，下面它的数字仍来自旧输入。
  • 耗时口径：所有方案都取客户端实测的单次往返时间，Jev 用 CLI 返回记录里的 elapsed_seconds，LLM 用调用前后的墙钟时间。各方案的中位数与 Bedrock 服务端记录的耗时最多相差 0.05 秒。

计价与 token 口径

  • 单价（你给定）：每百万输入 / 输出 tokens，Opus 5.5 是 $4 / $20，Haiku 5.5 和 GPT-6 Luna 都是 $0.10 / $0.50。Jev 每百万输入 $0.042，输出免费。本报告没有另行核实牌价。
  • token 取实测：全部来自服务端返回的记录。各家分词器不同，同样的输入，Claude 计得的 tokens 是 Jev 的 1.04 倍，GPT-6 Luna 是 0.74 倍。
  • 差距来源：Haiku 和 GPT-6 Luna 的输入单价是 Jev 的 2.4 倍，此外还要为输出付费，思考 tokens 也算在输出里。Opus 的输入单价是 Jev 的 95 倍。

自托管

自托管决策模型：Strands Decider 2B（自托管）

部署与计价

  • 模型：strands-decider-2B-qwen3.5-v1-2610，在 Qwen3.5-2B-Base 上加 LoRA 和读出头，和 Jev 一样属于决策模型。它部署在同一个 VPC 里，接口是 /v1/systemone，请求格式与 Jev 完全相同，76 个请求原样发送。
  • 实例：g5.xlarge，一张 24 GB 的 NVIDIA A10G，按需价格 $1.006/小时（AWS Pricing API: us-west-2, On-Demand, Linux, Shared tenancy; effective 2026-10-01）。token 不计费，成本只来自机时。
  • 本批次机时成本：$1.006/小时 × 10.76 秒 = $0.003007，是 Jev 的 1.20 倍。这个数字假设机器只为这批请求开着，是下限，实例空闲时同样在计费。
  • 常驻成本：全天开机约 $24.14/天。按 Jev 本次每个请求 $0.0000330 计算，每天要有约 732,646 个请求才能与 Jev 持平。本次串行实测的吞吐约为每秒 7.1 个请求，单机满负荷每天约 610,260 个，即使满负荷，每个请求也要 $0.0000396，仍是 Jev 的 1.20 倍。

发现的问题

  • 并发不安全：以并发 4 运行时，第一批请求就返回 HTTP 422，报错有这几条：HTTP 422: b'{"detail":"option span (260,281) has no tokens left; the prompt was truncated through its option list"}'，HTTP 422: b'{"detail":"option span (288,355) has no tokens left; the prompt was truncated through its option list"}'，HTTP 422: b'{"detail":"option span (298,344) has no tokens left; the prompt was truncated through its option list"}'。同一个请求串行发送时一切正常。另一次手动复现中，两个请求并发，其中一个失败，报错变成 zip() argument 2 is longer than argument 1，那次复现的结果没有单独存档。看起来服务端在并发时会把不同请求的状态混在一起，并发下即使返回 200，结果是否可靠也无法保证，这一点没有验证。因此本组结果是按并发 1 串行测得的，失败的那次调用记录原样保留在 llm-baseline-decider-concurrency4-failed-20261012.jsonl。
  • 评分题偏弱：17 个 score 题只有 6 个落在可接受区间，分布普遍很平，比如代码评审 H1 严重度三个等级的概率分别是 0.30 / 0.37 / 0.34。模型卡里也写明，score 和 noul 迁移到训练分布之外的评分标准时效果较差。
  • 付款步骤：结算页上，它以 0.797 的概率选了 click_e17（Click button "立即支付 ¥199.00".），只是因为略低于 0.8 的门槛才进入复核。门槛再低一点，这一步就会被放行，所以必须依赖调用方的硬拦截。
  • 直接选定却答错的判断（1 个）：jev-route:routing（五类任务的工具路由）· T2。

说明

局限

  • 价格采用你给定的数字，没有考虑 Bedrock 实际牌价，也没有计入批量和缓存折扣。系统提示很短，没有使用提示缓存。
  • 每个请求只跑了一次，没有测随机波动。
  • 准确率来自同一个作者编写的小样本，只反映这些用例上的表现，不能推广成普遍结论。
  • LLM 只给答案，Jev 还给出概率分布，可以直接设门槛做自动复核，纯成本对比没有计入这一差别。
  • 原始调用记录在 validation/v2/llm-baseline-20261012.jsonl（Opus）、llm-baseline-haiku-20261012.jsonl 和 llm-baseline-gpt6luna-20261012.jsonl，重建的请求在 llm-requests.json，脚本是 llm_baseline.py。记录文件里另有一组要求附一句理由的调用（style 为 reasoned），本报告没有采用。
